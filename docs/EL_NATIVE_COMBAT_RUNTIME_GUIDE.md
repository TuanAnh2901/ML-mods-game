# EL Native Combat Runtime Guide

## Build

Run `build.bat` from a Visual Studio 2022 x64 developer shell. The script emits
`injector.exe`, `el_native.dll`, and `combat_runtime_profiles_tests.exe` under
`D:\Temp\opencode\el_build`. It also builds the existing regression binaries.

The runtime waits for `GameAssembly.dll`, waits the overlay delay (default
2,000 ms, configurable with `EL_NATIVE_OVERLAY_DELAY_MS`), then initializes
the D3D11 overlay. No Ghidra CLI full analysis is required; RVA fallback data
is generated by the existing `tools/query_methods.py` and
`tools/gen_method_fallback.py` workflow.

## One-click launcher

Run `injector.exe`. On first launch it asks for a folder containing:

* `Everlusting Life.exe`
* `GameAssembly.dll`
* `UnityPlayer.dll`

The folder is stored in `%LOCALAPPDATA%\EL_Native\launcher.ini`. Later runs
create the process suspended, inject `el_native.dll`, resume the primary
thread, and append state transitions to `el_native_launcher.log` in the game
folder. Hold **Shift** or pass `--configure` to select a new folder. Every
failure path resumes the suspended thread before process cleanup.

If `steam_appid.txt` is present beside the executable, its numeric AppID is
exported as both `SteamAppId` and `SteamGameId` to the suspended child before
injection. This preserves Steamworks initialization even when the launcher is
started outside Steam. A manifest lookup is retained as a fallback; standalone
folders continue through the direct path and are logged as such.

## Profiles and settings

`el_native_profiles.json` is written beside the game executable. It contains
`schema_version`, `current_profile`, shared launcher/UI settings, and profile
objects containing enabled flags, sliders, filters, and typed feature settings.
Writes use a temporary file followed by atomic replacement and maintain
`el_native_profiles.json.bak`. A corrupt primary file can therefore be
recovered from the backup. Existing `el_native_config.ini` is read once when
JSON is absent and is left in place.

The typed `ConfigRegistry` supports boolean, integer, float, string, and hotkey
bindings. Profile persistence is manual: **Save current** writes live feature
flags/settings and **Load current** restores the selected profile. Switching
profiles applies the selected document immediately and does not copy the
previous profile's live toggles into it.
PvP coins are read-only through `ServerParticipant.get_Coins`; no coin mutation
hook is installed.

## Combat runtime and UI

`CombatRuntime` starts at `FieldController.StartBattle`, tracks unit pointers and
generations, and removes units on `BattleUnit.Dispose`. A snapshot is copied
under a mutex before rendering. Entity Manager rows show character, MonsterUid,
army side, grade, HP/mana, target, alive state, and hook call count. The
snapshot export button writes `el_native_entity_snapshot.txt`.

The shared hook registry records one owner per resolved address with
`Unavailable`, `Resolved`, `Hooked`, or `Conflict` status. Runtime hooks are
side-gated through the same army-side resolver:

* player turn interval = `originalInterval / multiplier`; enemy interval is unchanged;
* player multi-hit is clamped to 1–5 original calls;
* Freeze Enemy forces `IsNotTimeFrozen` false for enemy units only;
* Dumb Enemy blocks `AttackActivation` for enemy units while movement/target
  tracking remains untouched;
* damage, heal, offense, defense, and interval rows retain baseline/applied/delta
  values and call counts.

## A/B trace order

1. Observer: runtime session and Entity Manager only.
2. Rapid Fire: verify a player interval of `1.0` becomes `0.5` at 2x and enemy
   interval remains `1.0`.
3. Multi-hit: verify N values produce N original calls, with 0/6 clamped.
4. Freeze/Dumb Enemy: verify only enemy side changes.
5. Combat modifiers: enable heal/offense/defense and inspect comparison rows.

For each gate, inspect `el_native.log`, the hook status list, comparison
snapshots, and the absence of new network endpoint/payload types. Stop the A/B
run if resolution fails, a hook reports `Conflict`, a call count diverges, or
the match disconnects.

## Troubleshooting

* **Folder validation error:** confirm all three required files are in the
  selected folder; use `--configure` to replace the stored path.
* **Hook unavailable/conflict:** inspect `el_native.log` for method name and
  resolver source, then disable the feature. The registry prevents a second
  MinHook owner from replacing the first.
* **Overlay absent:** wait for D3D11 initialization, check
  `EL_NATIVE_OVERLAY_DELAY_MS`, and press Insert to toggle visibility.
* **Profile recovery:** close the game, rename the corrupt JSON, and copy the
  `.bak` file into place; the loader also exposes the same recovery path.
* **Rollback:** disable all features with End, close the game, restore the
  original DLL/EXE from the recorded backup, and run `rollback.ps1`.

## Verification and rollback artifacts

The implementation records the baseline hash manifest and the modified build
verification in `D:\Temp\opencode\el_native_verification.txt`. The runnable
rollback is `D:\Temp\opencode\el_native_rollback.ps1`; it restores the source
backup and removes generated build artifacts without touching `Tools Before`.

## Bunny/Rabbit roulette trace

The DLL includes `Bunny Royale Trace`. It hooks both roulette families found in
the current game build: `CardRouletteModel` server spin/progress parsing and
the `ChooseRewardRouletteEventModule` lot/choice/delivery path. These hooks are
observer-only: they return the original values and never edit rewards, the
selected index, delivery data, or network payloads. Enable the feature before
opening the event; the overlay lists up to five decoded cards and paints an
explicit `black/lose/fail/empty` token red. If the server only reports a
black-mark state without an index it deliberately shows `unknown` instead of
guessing. The raw response/choice/delivery trace is appended to
`el_native_roulette_trace.jsonl` for the one-shot event run.

## Compatibility, DevMenu and automation

Detector listener compatibility hooks are installed immediately after
`GameAssembly.dll` appears (25 ms polling, 30 s timeout) and are restored on
DLL detach. They are memory-only MinHook hooks; generic network-error windows
remain visible for diagnostics. The AntiCheat Diagnostics panel shows each
target's resolver and hook status.

DevMenu opens `CheatsWindow` through the validated sequence
`.cctor -> LoadWindow -> get_instance -> Show`, one step per main-thread frame,
including inherited generic methods and their `MethodInfo`. The native fallback
map includes the concrete `CheatsWindow` aliases for the current
`WindowScriptCore<T>` implementation.

`BattleResult` force-win now covers the local result converter plus
`LocalServerEmulator.BattleResult` winner selection and the local
`ChessSocketsController.BattleResult/BattleCalculateResult` request paths plus
the local `ServerParticipant.UpdateStreaks` path used by Tournament/session
progression.
The overlay reports each path separately, making a Tournament run easy to
verify in the log.

Automation has a shared `AutoBattle/Derank` coordinator with bounded loops and
main-thread dispatch. AutoBattle now schedules `MainWindowPlayButton.OnPlayClick`
and advances `MatchCompletedWindow` after the configured delay. Derank uses the
extracted settings → surrender → confirmation phases only when its three field
offsets resolve through metadata; stale offsets are not guessed. Bunny's
Python companion is configured via `bunny.companion_path` and is never spawned
or proxied by the DLL.

### Mascot session unlock

Enable **Mascot Trace** and **Unlock all mascots (session)**, then close and
reopen the mascot window. `MascotWindowPresenter.InitMascotButtons` expands the
managed collection from the mascot dictionary before the normal UI builds its
buttons. Select the added mascot through the game UI. `MascotWindow.OnHidden`
restores the original list, so this is a session-local UI unlock rather than an
account inventory mutation. When metadata exposes the extracted transient
request-guard fields, the feature clears them while this toggle is active so a
409 from the mascot endpoint does not stall later profile/quest requests. The
overlay shows getter/hook status and the final collection count.

### Bunny Royale one-shot checklist

1. In **Experimental → Bunny Royale Trace**, set **Python companion path** to
   the companion script/executable. Start that companion yourself; the DLL does
   not create a Python process or intercept the network.
2. Inject the current `el_native.dll`, open the overlay, and enable the trace
   before entering the event. Leave `NetLog` enabled if you also want endpoint
   timing in `el_native.log`.
3. Open the Monday event and wait until the overlay shows a `cards` snapshot
   and a `server_response` line. Do not select a card while the snapshot is
   empty or marked `unknown`.
4. The overlay marks a card red only when the server payload contains an
   explicit `black`, `lose`, `fail`, `nothing`, or `empty` token. A response
   that reports only a black-mark boolean has no safe index and is shown as
   **unknown** rather than guessed.
5. Preserve `el_native_roulette_trace.jsonl` and the matching time window in
   `el_native.log`; this is the evidence for a later decoder update. The hooks
   call each original method exactly once and do not rewrite rewards or choice
   payloads, so the event remains a single-shot trace.
